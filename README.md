# КиноПлан — сервис планирования киносъёмок

Сервис хранит фильмы и сцены, локации и график съёмок, проверяет доступность
площадок и формирует статистику. Основные пользователи — режиссёры,
ассистенты и администраторы съёмочного процесса.

## Установка и запуск

Python 3.11+, Django 5.2, SQLite, Bootstrap 5.3, pytest, flake8.

```bash
python3.11 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py import_legacy
python manage.py runserver
```

Открыть http://127.0.0.1:8000/. Импорт выполняется один раз в пустую базу ORM.
Если данные уже перенесены, повторять команду не нужно: существующие записи
не перезаписываются. Путь источника можно задать `--source /path/source.sqlite`.
Источник ПР7 `data/kinoplan.sqlite` открывается только для чтения. Новые таблицы
Django создаются в исключённой из Git базе `db.sqlite3`. Данные переносит
`shootings/management/commands/import_legacy.py` одной транзакцией с сохранением
идентификаторов и связей. Структуру базы воспроизводят миграции в приложениях.

## Модели и правила

- `films.Film`: название, режиссёр; `films.Scene`: фильм, номер, описание, группа.
- `locations.Location`: название, адрес, положительная вместимость.
- `shootings.Shooting`: сцена, локация, дата и `status` из `TextChoices`
  (`active`, `cancelled`, `completed`).
- Фильм содержит сцены (CASCADE); съёмки защищают свои сцены и локации от
  удаления (PROTECT). `related_name` предоставляет обратные связи.
- Уникален номер сцены в фильме. Отменённые и завершённые записи не занимают площадку. Нельзя назначить
  две активные съёмки на
  одну площадку в один день. Группа должна помещаться на площадке.

## Страницы

| Адрес | Возможности |
| --- | --- |
| `/` | Сводка и ближайшие съёмки |
| `/films/`, `/films/<id>/` | Поиск фильмов, сцены и съёмки фильма |
| `/locations/`, `/locations/<id>/` | Поиск по названию или адресу, `capacity`, проверка занятости `date` |
| `/locations/free/?date=2026-11-10&crew=40` | Свободные площадки подходящей вместимости |
| `/shootings/`, `/shootings/<id>/` | График и карточка съёмки |
| `/shootings/statistics/?min=2` | Итоги, загрузка локаций, группы по фильмам, месяцы, сцены без съёмок |

График поддерживает `q`, `film`, `location`, `date`, `status=active/cancelled/completed`,
`sort=date/-date/film/location`, `page`. Сортировка задаётся белым списком;
пагинация по 5 записей сохраняет параметры. Отсутствующий объект даёт 404,
пустые результаты сопровождаются сообщением, некорректные фильтры не вызывают 500.

## Административная панель ПР10

```bash
python manage.py createsuperuser
python manage.py runserver
```

Адрес: http://127.0.0.1:8000/admin/. В текущем локальном окружении создан
администратор: реквизиты сохранены в `.env.local` (права 600, исключён из Git).
На новой установке для своей учётной записи задайте имя и
пароль интерактивно; паролей и готовых администраторских сессий в репозитории нет.
Film, Scene, Location и Shooting зарегистрированы с русскими названиями.
Настроены столбцы, поиск по связанным полям, фильтры статуса/даты/фильма/локации,
сортировка, date_hierarchy, readonly_fields и autocomplete. В фильме можно
редактировать сцены inline, в локации — связанные съёмки. Кнопка «Смотреть на
сайте» использует get_absolute_url(). Массовые действия отменяют, завершают или
активируют записи; при конфликте активации вся операция откатывается с сообщением.

### Статусы и миграция данных

Миграция `shootings/0002_status_choices` добавляет status, переносит отменённые
записи, помечает прошедшие неотменённые съёмки завершёнными относительно даты
применения миграции и удаляет старый флаг. Состояние на 9 ноября 2026 года:
4 активных, 1 отменённая, 2 завершённых из 7. Дальнейшее завершение выполняется
явно в админке: дата сама не переписывает сохранённый статус. Обратная миграция
сохраняет отмену; прежняя булева схема не различает активные и завершённые.

Менеджер `ShootingManager` и `ShootingQuerySet` в `shootings/managers.py`
предоставляют цепочки `active()`, `cancelled()`, `completed()`, `on_date()`,
`search()`, `with_related()`, `with_capacity_margin()`. Резерв вместимости
вычисляется через `F(location__capacity) - F(scene__crew_size)` и показан в карточке.
`Location.objects.available_on(date)` исключает только активные съёмки этой даты.
Итоги статистики отдельно считают все три статуса.

### Локации и общий контекст

Миграция `locations/0002_slug_and_large` создаёт уникальный ASCII-slug для
существующих названий и GeneratedField `is_large` (capacity >= 50). Новые имена
транслитерируются, одинаковые названия получают разные суффиксы. Изменение имени
не меняет slug автоматически; его можно явно отредактировать в админке.
Канонический адрес: `/locations/place/<slug>/`; числовые адреса ПР5 сохранены.
Значение `is_large` вычисляет SQLite при изменении вместимости, вручную оно не
редактируется. Контекстный процессор `homepage.context_processors.site_context`
передаёт название сайта и число локаций в общий подвал.

## Слой данных и структура

Веб-представления вызывают `db/queries.py`, который теперь целиком использует
Django ORM. Функции содержат более 15 различных выражений: получение списков и
карточек, фильтры связанных моделей, `exclude`, `Q`, `values`, `select_related`,
`aggregate`, `annotate`, `Count/Sum/Avg/Min/Max`, сортировку и срезы. В статистике
локации без съёмок остаются с нулевым счётчиком. График загружает связанные
сцену, фильм и локацию одним JOIN, избегая N+1.

CRUD с валидацией и транзакциями находится в `shootings/services.py`.
`python manage.py orm_demo` создаёт, читает, меняет и удаляет учебные объекты,
выполняет `F`-выражение и откатывает транзакцию.

- `kinoplan/`: настройки и корневые URL.
- `homepage/`, `films/`, `locations/`, `shootings/`: Django-приложения.
- `templates/base.html`, `templates/includes/`: общий каркас, навигация, пагинация.
- Шаблоны страниц находятся внутри приложений, статика — в `homepage/static/`.
- `models/`, `storage.py`, `main.py`: сохранённая консольная версия ПР3 с JSON.
- `db/database.py`, `db/import_json.py`, `sql/`: учебный слой SQLite ПР7;
  веб-интерфейс больше не выполняет его ручные SQL-запросы.
- `tests/`: прежние тесты консоли, SQLite и страниц, новые проверки ORM.
- `report/`: прежние отчёты; `reports/`: отчёты ПР9 и последующих работ.

## История изменений по практическим работам

### ПР1. Основы Python: актуализация знаний и настройка рабочего окружения

Что сделано:

- выбрана тема проекта, создан Git-репозиторий и удалённый репозиторий на GitHub;
- настроено виртуальное окружение `venv` и конфигурация отладки VS Code;
- создан `.gitignore` и заполнен `README.md` (назначение, аудитория, предметная область, сущности, функции, план развития);
- в `main.py` реализован начальный сценарий: данные одной сцены хранятся в переменных простых типов, дата задаётся через модуль `datetime`;
- реализованы функции `check_location_availability()`, `get_days_until_shooting()`, `get_shooting_status()`.

Отладка: в `main.py` была намеренно внесена ошибка — в функции `get_days_until_shooting` порядок вычитания дат был перепутан (`today - shoot_date` вместо `shoot_date - today`), из-за чего дата съёмки в будущем ошибочно определялась как уже прошедшая.

1. Установлен breakpoint на строке вычисления `delta` в функции `get_days_until_shooting`.
2. Программа запущена в режиме отладки IDE.
3. Выполнение пройдено пошагово до точки останова.
4. Проверены значения переменных `today`, `shoot_date` и `delta.days` — обнаружено, что `delta.days` отрицательное, хотя дата съёмки позже текущей.
5. Причина ошибки установлена: перепутан порядок операндов при вычитании дат.
6. Ошибка исправлена на `delta = shoot_date - today`, работа программы проверена повторным запуском.

### ПР7. Основы баз данных и SQL

Что изменилось по сравнению с ПР6:

- **база данных:** `data/kinoplan.sqlite`, таблицы `films`, `scenes`, `locations`, `shootings` в `sql/schema.sql`; первичные и внешние ключи, `NOT NULL`, `DEFAULT`, `CHECK`, `UNIQUE`; сцены вынесены из фильма в отдельную таблицу;
- **правило двойного бронирования в базе:** частичный уникальный индекс не даёт назначить две активные съёмки на одну локацию в один день;
- **работа из Python:** `db/database.py` (подключение, `PRAGMA foreign_keys = ON`, `sqlite3.Row`), `db/import_json.py` (перенос JSON → SQLite через `executemany`, транзакция с `commit`/`rollback`, повторный запуск безопасен);
- **SQL-запросы:** 25 запросов в `sql/queries.sql`, проверены в SQLite CLI; выборка, WHERE (`=`, `>=`, `BETWEEN`, `LIKE`, `IS NULL`), JOIN и LEFT JOIN, подзапрос `NOT IN`, `COUNT/MIN/MAX/AVG/SUM`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT/OFFSET`, `DISTINCT`;
- **веб-интерфейс на SQLite:** все страницы получают данные запросами из `db/queries.py` (19 функций), значения передаются параметрами `?`; новые страницы — поиск свободных локаций на дату (`/locations/free/`) и статистика (`/shootings/statistics/`), подбор локаций по размеру группы, пункт «Статистика» в навигации;
- **предметная логика:** текст статуса вынесен в `get_status_text()` и используется и объектом `Shooting`, и строками из базы; функция ПР1 `check_location_availability()` по-прежнему формирует сообщение о занятости;
- **данные:** добавлена сцена без съёмки, чтобы запрос `LEFT JOIN … IS NULL` возвращал непустой результат;
- **тесты:** `conftest.py` собирает временную базу из JSON и подменяет `DB_PATH`; `tests/test_database.py` проверяет схему, внешние ключи и ограничения, импорт, запросы WHERE/JOIN/GROUP BY/HAVING и новые страницы (всего 81 тест).
